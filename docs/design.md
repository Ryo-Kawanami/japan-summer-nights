# 日本の夏は、夜が暑くなった — 設計書

作成日: 2026-07-26

## 1. これは何か

JAXA Earth API for Python が配信する衛星の地表面温度データを使い、**日本の夏の暑さが25年でどう変わったか**を、誰でも触れる1画面のWebアプリとして伝える。

当初の狙いは「日本の夏が暑くなった様子を時系列で見せる」ことだった。しかし設計前の実データ検証により、**昼間の地表面温度には統計的に有意な温暖化トレンドが存在しない**ことが判明した。一方で**夜間には明確なトレンドがある**。

この発見をアプリの中心に据える。伝えたい結論は次の一文である。

> **昼は変わっていない。暑くなったのは夜だ。**

## 2. 検証で確定した事実

すべて実データを取得して確認済み。推測ではない。

### 2.1 データソース

```
コレクション: NASA.EOSDIS_Terra.MODIS_MOD11C3-LST.{daytime|nighttime}.v061_global_monthly
バンド:       "LST"（単位: ケルビン。摂氏へは -273.15）
解像度:       0.05度（約5km）/ ppu=20
空間:         陸地のみ有効、海はNaN
配信期間:     2000-02 〜 2025-05
```

- 夏（6・7・8月）は **2000年〜2024年の25年が欠損ゼロ**で揃う。
- 2025年の夏はまだ配信されていない。`filter_date` に 2025-06 以降を渡すと
  `Exception: Error! No date list found!` で落ちる。**上限は2024年**。
- bbox `[122.0, 24.0, 146.0, 46.0]`（ppu=20）で **440×480 グリッド**。
  MODIS の陸ピクセルは約 54,900 個だが、そのうち **日本の陸地は 15,883 個**。
  残りは韓国・ロシア・中国大陸で、集計にも地図にも入れない。
  沖縄（北緯26度）を含めるため南端を24度まで下げてある。

### 2.2 取得結果の形

`get_images()` の戻り値は `ImageCollection` で、配列は **`d.raster.img`** にある。
形状は `(時間, 緯度, 経度, バンド)`。`d.img` は存在しない。

```python
from jaxa.earth import je
d = (je.ImageCollection(collection=COL)
       .filter_date([f"{y}-06-01T00:00:00", f"{y}-08-01T00:00:00"])
       .filter_resolution(ppu=20)
       .filter_bounds(bbox=[122.0, 24.0, 146.0, 46.0])
       .select("LST")
       .get_images())
img = np.array(d.raster.img, dtype="float32")[..., 0]   # (3, 440, 480)
```

`filter_date` の終端は**含む**。`06-01 〜 08-01` で 6・7・8月の3枚が返る。

注意: 返り値の `cinfo` 属性は `ColorInfo` オブジェクトの ndarray で、
`np.nanmin` 等をかけると `TypeError` になる。触らないこと。

### 2.3 全国平均トレンド（夏6-8月、日本の陸地のみ）

| | トレンド | 相関 r | t値 | 正のトレンドを持つ陸ピクセル |
|---|---|---|---|---|
| **昼間** | +0.260 ℃/10年 | +0.375 | 1.94 | 86.0 % |
| **夜間** | **+0.636 ℃/10年** | +0.637 | **3.96** | **99.9 %** |

有意判定には |t| > 2.07 が必要（n=25, 両側5%）。**昼間は有意でない。夜間は有意。**

昼間の t=1.94 は判定境界のすぐ下にある。「昼は変化がない」ではなく
**「年ごとのばらつきが大きく、25年では傾向を取り出せない」**が正確な言い方で、
画面の文言もそう書くこと。断定すると数字を超えた主張になる。

### 2.4 5年平均どうしの比較（アプリが表示する数字）

| | 2000-2004 | 2020-2024 | 差 | 年々の標準偏差 |
|---|---|---|---|---|
| **昼間** | 24.72 ℃ | 25.31 ℃ | **+0.59 ℃** | ±0.50 ℃ |
| **夜間** | 16.17 ℃ | 17.69 ℃ | **+1.51 ℃** | ±0.72 ℃ |

25年平均を基準にした平年差の分布（5%タイル / 95%タイル）:

- 昼間 前期 −0.92 / +0.32、後期 −0.19 / +0.94 → **まだら。方向が揃っていない**
- 夜間 前期 −1.13 / −0.05、後期 **+0.40 / +1.48** → **陸のほぼ全域が青から赤へ**

平年差の表示レンジは **±2.0℃**。実測でレンジ外に出る画素は最大 0.04% で、
±1.5℃ にすると夜の後期が 4.3% 飽和して構造が潰れる。

（※ 初版では bbox が狭く大陸を含んでいたため、昼 +0.086 / 夜 +0.561℃/10年 だった。
日本の陸地に限定し沖縄を含めた結果、上記の値に変わった。）

### 2.5 なぜ昼は見えないのか（アプリ内で説明する内容）

MODIS の LST は**晴天時しか観測できない**。日本の夏は雲と雨が多いため、月平均は
「その月にたまたま晴れた日」の寄せ集めになる。梅雨の長短で年ごとのサンプリングが
大きく変わり、これが昼間の年々変動（σ=0.50℃）を生んで、
25年分でも +0.59℃ しかないトレンドを埋めてしまう。

夜間は日射と土壌水分の影響が抜けるため、同じ雲バイアスがあってもシグナルが残る。
これは気象庁が報告している「熱帯夜の増加が日中最高気温の上昇より速い」という
現象と整合する。

## 3. スコープ

### 作るもの

日本全域を1画面に収めた、**Before/After スライダー地図 + 折れ線グラフ**の静的Webアプリ。

```
┌──────────────────────────────────────┐
│  日本の夏は、夜が暑くなった                 │
│                                      │
│           [ ☀ 昼 ] [ 🌙 夜 ]           │  ← 主トグル（発見そのもの）
│                                      │
│    2000-2004  ││  2020-2024          │
│       ░░░░    ◀▶    ▓▓▓▓             │  ← 日本地図・中央ハンドルを左右に
│       ░░░░    ││    ▓▓▓▓             │
│                                      │
│    昼 +0.59℃   ／   夜 +1.51℃          │
│                                      │
│  ┌────────────────────────────────┐  │
│  │ 香川県・夏の地表面温度              │  │
│  │  夜 ······················╱▔     │  │  ← 昼夜2本、25年
│  │  昼 ─────╲───╱────────╲──       │  │
│  │ 2000 ───────────────────── 2024 │  │
│  └────────────────────────────────┘  │
│  ⚠ 気温ではなく衛星が測る地表面温度         │
│  ⚠ 晴れた日のみ観測（雲の下は測れない）      │
└──────────────────────────────────────┘
```

**操作は3つだけ。**

1. 昼/夜トグル — 切り替えると地図の赤さが劇的に変わる。これが結論を運ぶ。
2. スライダーを左右に拭う — 前期と後期を比較する。
3. 地図をクリック — その都道府県の25年折れ線がグラフ欄に出る。

### 地図のスケール設計（重要）

主地図は**実測温度**を、昼夜・前後期すべて共通の1本のスケール（5〜40℃）で塗る。

初期版では両パネルを「25年平均からの差」で塗っていた。しかしその塗り方では
**前期は定義上ほぼ必ず平均より低く（青）、後期は高く（赤）なる**。
実際の差が +0.59℃ でも +1.51℃ でも、同じ青→赤のフルスイングに見えてしまう。
1枚の地図の中の空間差が 12〜17℃ あるのに対し時間変化は 0.6〜1.5℃ しかないので、
これは10分の1の量を同じ迫力で見せることになる。結論を絵で作りに行っている。

変化量は**別のアセット**として「後期 − 前期」を昼・夜それぞれ1枚ずつ出す。
ゼロを中心とした発散配色（±3℃）で、昼と夜を同じスケールで並べる。
差を見せるならこれが正しい形で、左右で色を仕込む必要がない。

配色は用途で分ける。実測温度は順序尺度なので単調なランプ——温度は
「セマンティック・ヒート」に当たるため淡黄→橙→深紅の多色ランプが使える。
条件は明度が単調に下がることと、凡例に実数値を添えること。
変化量は極性を持つので発散配色、中点は無彩色。

### 作らないもの（明示的な非目標）
- **年を自由に選ぶUI** — 25年分のグリッドを全部フロントに載せる必要が出て転送量が桁で増える。
- **街区レベルのズーム** — GCOM-C/SGLI 250m は2018年以降しかなく「25年の変遷」を語れない。
- **衛星データからの猛暑日カウント** — 月平均なので日数を数えられない。
  日数の指標は後から追加した気温データ（日別）で出している。
- **2025年のデータ** — 未配信。
- **バックエンドAPI** — 全アセットを事前に焼くので不要。

## 4. アーキテクチャ

```
[ビルド時 1回・Python]                    [実行時・静的配信]

jaxa-earth で取得                          ブラウザ
  ↓ 25年 × 2(昼夜) × 3ヶ月                   ↓ fetch
夏平均グリッド (440×480)                    assets/*.png, *.json
  ↓ 集約                                    ↓ decode
① 実測温度グリッド 4枚 → PNG (uint8)    →   canvas に直描き（投影不要）
  変化量グリッド 2枚 → PNG (uint8)
② 都道府県コードラスタ → PNG            →   クリック座標→県ID の逆引き
③ 都道府県別 25年系列 → JSON            →   自前SVGで折れ線
```

**総ペイロードは実測 196KB**。サーバー不要。Cloudflare の静的アセット配信に置いている
（アセットへのリクエストは無料・無制限なので、アクセス数による課金は発生しない）。

### 4.1 前処理パイプライン（Python）

`pipeline/` 配下に、責務ごとに分けた小さなモジュールを置く。

| モジュール | 責務 | 入出力 |
|---|---|---|
| `fetch.py` | JAXA Earth API から年×昼夜の夏平均グリッドを取る。取得済みは `.npy` にキャッシュして再取得しない | (year, daynight) → `(440,480) float32` ケルビン |
| `aggregate.py` | 5年平均・25年平均・平年差・トレンド・都道府県平均を計算する。**ネットワークに触れない**ので単体テストできる | grid stack → 各種派生配列 |
| `encode.py` | 配列を uint8 PNG に量子化、系列を JSON に書く | 配列 → `web/public/data/*` |
| `prefectures.py` | 都道府県ポリゴンを 440×480 のコードラスタにラスタライズ（ビルド時1回） | GeoJSON → `(440,480) uint8` |
| `landcover.py` | ALOS 土地被覆図から5kmセルごとの市街地率を作る | 土地被覆 → `(440,480) float` |
| `weather.py` | 気温・湿度を Open-Meteo から取る（ERA5 / CMIP6 / モデルの過去） | 地点×年 → 日次配列 |
| `weather_stats.py` | 熱帯夜・猛暑日・体感温度・基準期間比の日数 | 日次 → 年ごとの指標 |
| `heatstroke.py` | 消防庁の熱中症搬送者数 | xlsx → (年, 県) |
| `biascorrect.py` | 気候モデルと再解析の系統差を差分法で打ち消す | モデル日次 → 補正済み |
| `interp.py` | まばらな観測点を解析グリッドへ広げる | 地点値 → グリッド |
| `downscale.py` | ML の特徴量と検証（年ブロックCV／暖年抜き取り／外挿範囲） | 特徴量 → 検証結果 |
| `build_pref_future.py` | 県別の学習・予測・`future.json` 書き出し | 全部 → JSON |

`fetch.py` は1年あたり数十秒かかる。**キャッシュ必須**（検証時の実測: 25年分で約10分）。

分離の理由: `aggregate.py` が純粋関数の集合になるので、
既知の入力配列を与えて期待値を検証するテストが書ける。
数字の正しさがこのアプリの価値の全部なので、ここは必ずテストする。

### 4.2 量子化の設計

実測温度グリッドは `5.0 〜 40.0 ℃`、変化量グリッドは `-3.0 〜 +3.0 ℃` を
1-255 にマップし、0 を NaN（海・国外）に予約する。
刻みはそれぞれ 0.138℃ と 0.0236℃ で、表示上まったく問題ない。
PNG のグレースケール1chで焼き、色付けはフロントの canvas 側で行う
（カラーマップをコードで持てるので、後から色を変えてもアセットを焼き直さなくて済む）。

### 4.3 フロントエンド（Next.js + Tailwind）

`shin_nextjs` と同じ構成（Next.js + Tailwind、App Router）。
`output: 'export'` で静的書き出しする。

| コンポーネント | 責務 |
|---|---|
| `MapCompare` | PNG をデコードして canvas に描き、スライダーで前後期を拭う。等緯度経度グリッドなので**投影計算は不要**、矩形にそのまま貼れる。カーソル位置の実温度も読み出す |
| `DiffMaps` | 「後期 − 前期」の変化量を昼夜で並べる。ゼロ中心の発散配色 |
| `TrendChart` | 25年×2系列の折れ線を自前SVGで描く。チャートライブラリは入れない |
| `FutureChart` | 実測と予測を1本の線でつなぐ。予測部分は破線、境界に縦線と文字 |
| `AirLstScatter` | 気温と地表面温度の散布図。1:1 の基準線で上下を読ませる |
| `Explainer` | 専門用語のその場解説（details/summary） |

地図描画もグラフも `dataviz` スキルの指針に従って設計する。
特にカラーマップは、平年差なのでゼロを中心に据えた発散型を使い、
色覚特性に依存しない配色にする。

## 5. 誠実さの要件（機能要件として扱う）

このアプリは科学データを一般向けに提示する。数字が独り歩きしやすいので、
以下を**実装必須項目**とする。

1. **「気温」と書かない。** 常に「地表面温度」と表記する。
   初回表示時に、気温との違いを1文で説明する注記を出す。
2. **観測の限界を隠さない。** 「晴れた日のみ観測」を画面上に常時表示する。
3. **昼のデータを削除しない。** 「有意でなかった」という結果ごと見せる。
   これが「夜だけが上がった」の証拠になっている。
4. **出典を明記する。** MODIS MOD11C3 (Wan, Z., Hook, S., Hulley, G. 2021, NASA EOSDIS LP DAAC,
   doi:10.5067/MODIS/MOD11C3.061) と
   JAXA Earth API、および JAXA のデータ利用ポリシーへのリンクを常時表示する。
5. **数字に幅を添える。** 全国平均の差を出す箇所には、年々変動の大きさ
   （昼 σ=0.50℃ / 夜 σ=0.72℃）を併記する。

## 6. 検証方法

### 単体テスト（`pipeline/tests/`）

- `aggregate.py` の各関数に既知の小さい配列を与え、平均・偏差・トレンドの
  期待値と一致することを確認する。
- NaN（海）が平均に混入しないことを確認する。**回帰しやすい箇所。**
- 量子化 → 復号 のラウンドトリップ誤差が 0.05℃ 未満に収まることを確認する。

### 数値の受け入れテスト

前処理の最終出力から次の値を計算し、本設計書 §2.3 / §2.4 の表と一致することを確認する。
一致しなければパイプラインのどこかが壊れている。

```
夜間 2000-2004 平均 = 16.17 ℃ (±0.01)
夜間 2020-2024 平均 = 17.69 ℃ (±0.01)
昼間の差            = +0.59 ℃ (±0.01)
夜間トレンド        = +0.636 ℃/10年 (±0.005)
昼間トレンド        = +0.260 ℃/10年 (±0.005)  ← t=1.94 で有意でないこと
```

`pipeline/_probe/visual_check.py` を走らせると、この値の確認と地図の目視用画像の
生成を同時に行える。地理の健全性（緯度と夜間温度の相関が負、南が北より暖かい）も
そこで自動判定する。地点ごとの厳密な単調性は成り立たない——東京は都市の影響で
鹿児島より夜が暑い——ので、判定は全画素の相関で行うこと。

### 手動確認

`npm run dev` で起動し、以下を目視する。

1. 昼トグルで地図がほぼ白い。夜トグルで日本列島全体が赤い。
2. スライダーを端から端まで動かして、境界が滑らかに追従する。
3. 北海道・東京・沖縄をクリックし、それぞれ異なる折れ線が出る。
4. スマートフォン幅で横スクロールが発生しない。
5. 注記と出典が常に見えている。

| 昼の有意性が境界上 | t=1.94 と判定値 2.07 の差が小さい。基準期間や範囲の取り方次第で有意側に振れうる | 断定を避ける文言で対応。数字は画面に常時表示 |

## 8. 実装の順序

1. `pipeline/fetch.py` + キャッシュ（既に検証スクリプトがあるので流用できる）
2. `pipeline/aggregate.py` + テスト → §6 の受け入れ値で検証
3. `pipeline/prefectures.py`（ポリゴン入手を先に確定）
4. `pipeline/encode.py` → アセット出力
5. Next.js 雛形 + `MapCompare`（まず1枚描く）
6. `DiffMaps` → `TrendChart` → `FutureChart`
7. 注記・出典・レスポンシブ対応
8. 静的書き出しとデプロイ

1. 気温・湿度との連動を見る
2. 当時の人がどれだけ暑いと感じていたか

あわせて「なぜ上がっているのか」の考察と、「何の役に立つのか」も求められた。

| 用途 | データ | 期間 |

| 気温・湿度（将来） | CMIP6 MRI_AGCM3_2_S（気象研究所、約20km） | 2025-2050 |

## 設計上の判断と、その理由

### 「特に暑い日」を絶対値で数えない

再解析は10〜30km格子の平均なので、都市の尖った最高気温がならされる。
実測で猛暑日13日あった2010年の東京が、このデータでは0日になる。
熱帯夜も2011年の東京で9日（実測は30日超）。絶対しきい値は使えない。

各地点の基準期間（2000-2004）の90パーセンタイルをしきい値にする。
偏りは分子と分母の両方に同じようにかかるので大きく相殺される。
検算: 基準期間の日数は全国平均8.7日（理論値9.2日）、暑かった2004年は12.0日。

### 予測は「年の外挿」ではなく「関係の学習」

地表面温度を年で外挿すると、学習点25個の直線当てはめに名前を付けただけになる。
学ぶのは「その年の気象とその土地の性質 → 地表面温度」の関係で、年は説明変数に入れない。
将来は同じ関係に気候モデルの気象を入れる。

検証は2種類。年ブロック交差検証（セル単位で分けると同じ年の似た行が学習側に残り
精度を過大評価する）と、2000-2019で学習して2020-2024を当てる暖年抜き取り。
後者は「見たことのない暖かさへの転移」そのもの。

| | CV R² | 暖年 R² | RMSE | 偏り | |
|---|---|---|---|---|---|
| 昼 線形 | 0.858 | 0.849 | 0.88℃ | +0.13℃ | ← 採用 |
| 昼 GBM | 0.911 | 0.864 | 0.83℃ | +0.37℃ | |
| 夜 線形 | 0.826 | 0.791 | 0.98℃ | −0.26℃ | |
| 夜 GBM | 0.921 | 0.880 | 0.75℃ | −0.16℃ | ← 採用 |

普通の交差検証だけで選ぶと内挿が上手いだけのモデルを選んでしまうので、
暖年抜き取りの誤差と偏りで選ぶ。木モデルは学習範囲の外を外挿できないが、
将来の入力が学習範囲を超えるのは湿度の2.0%だけだった。

### 気候モデルと再解析の系統差を差分法で消す

予測を作って中身を見たら、東京の夏の平均最低気温が
2024年(ERA5) 23.07℃ → 2025年(MRI) 22.24℃ と逆行していた。
20km格子のモデルが都市のヒートアイランドを解像しないためで、
将来が涼しいのではなく物差しが違うだけ。全国平均では偶然つながって見えていた。

モデルの絶対値は使わず、モデル自身の基準期間からの変化量だけを実測に足す。
補正できないうちは将来の数字を一切出さない。

## 確定した数字

```
熱中症搬送者数との関係（2010-2024、n=15）  生の相関 / トレンド除去後
  特に寝苦しい夜の日数    +0.821 / +0.777  有意 (t=4.46)
  体感温度                +0.624 / +0.573  有意 (t=2.52)
  夏の平均最低気温        +0.612 / +0.552  有意 (t=2.39)
  夜の地表面温度          +0.590 / +0.413  有意でない (t=1.63)

10年あたりのトレンド
  夜の地表面温度 +0.636℃   昼 +0.260℃
  最低気温       +0.375℃   最高気温 +0.729℃
  特に寝苦しい夜 +6.40日

気温1℃あたりの地表面温度の応答
  夜 +1.17℃ (r=0.86)   昼 +0.85℃ (r=0.61)
```

このサイトの主題である衛星の地表面温度が、熱中症の説明力では気温ベースの指標に
負けている。人が倒れるのは地面ではなく空気の温度と湿度なので筋は通っており、
自分に不利な結果もそのまま載せる。

## 踏んだ落とし穴

- Open-Meteo の利用枠は「地点数 × 変数 × 日数」で重み付けされる。
  912地点 × 7変数 × 92日 で取りに行って毎時上限、続けて日次上限まで使い切った
- 作り直した後も古いプロセスが生きたまま枠を食い続けていた
- 日次上限を1分待ちで叩き続ける再試行ロジックになっていた
- 統合処理が未取得の年に当たると自分でも取得を始め、背景ジョブと競合する構造だった
- 消防庁データのシート名の区切りが年で違い（2013_06 と 2013.07 が混在）、
  7月と8月を黙って取りこぼして2013年が4,265人になった（正しくは55,596人）
- 全国平均の取り方が面積加重と県平均で混在し、相関が 0.41 と 0.66 に割れた
- シェルスクリプトで変数の直後に全角文字を置き、bash が変数名の一部と読んだ
